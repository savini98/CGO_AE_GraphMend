# Per-model evaluation harness

This is what C1 and C2 actually run. For each model it builds the model, runs
the forward pass through a counting backend twice, GraphMend off then on, and
reports the breaks before and after and whether the output changed.

[`artifact/run_break_analysis.sh`](../artifact/run_break_analysis.sh) calls
into this harness, and that is the normal way to run it. Use the commands here
when you want a single model, a different subset, or the per-break explanation.

No GPU required. The latency claims are in
[`artifact/README.md`](../artifact/README.md).

## What is here

```text
paper_eval/
├── registry.py       # the models: how each is built, and what input it gets
├── entry.py          # the measurement program, run under `jac run`
├── run_eval.py       # C1: two arms, break counts and output fingerprints
├── run_fullgraph.py  # C2: torch.compile(fullgraph=True) on both arms
├── run_why.py        # why a given break survived
├── why.py            #   the report it drives
└── _paths.py         # where the patched toolchain and the harness live
```

## Before you run

`bash scripts/setup.sh` must have been run once. It applies
`patches/graphmend.patch` to the pinned `jaseci/` submodule and fetches the
typeshed stubs. Without it nothing compiles.

The patched toolchain must be the `jaclang` that gets imported, not a
pip-installed one, since every released `jaclang` predates GraphMend.
`_paths.py` arranges that for every arm subprocess.

You also need `torch==2.12.1` and `transformers==4.52.4`, the paper's pinned
versions.

## Run

From the repository root:

```bash
python -m paper_eval.run_eval                          # offline models (default)
python -m paper_eval.run_eval t5-small biogpt          # a subset
python -m paper_eval.run_eval MoLFormer-XL-both10pct   # opt-in, needs network

python -m paper_eval.run_fullgraph                     # C2, all rows
python -m paper_eval.run_fullgraph t5-small            # C2, a subset
```

To see why a model still breaks, which is what tells a correct 0% row apart
from a bug:

```bash
python -m paper_eval.run_why longformer-base-4096 on
```

Expect the first run of each model to be slow. GraphMend recompiles the
imported modeling code through the Jac front end, and on a cold cache that is
minutes per arm. Later runs hit the module cache.

## How the two arms differ

GraphMend has no CLI switch. It is controlled by two `jac.toml` keys, and
`run_eval.py` writes a fresh `jac.toml` per arm into a temp working directory:

```toml
[run]
graphmend = true                # on by default
graphmend_claim_imports = true  # opt-in: let GraphMend claim imported .py code
```

`graphmend_claim_imports` is the one that matters here and is **off by
default**. Model code lives in an imported third-party package, so without it
GraphMend transforms nothing and both arms measure the same thing. That is the
first of two mistakes that silently disable GraphMend. The second is below.

## The entry program must be compiled by Jac

That is the second mistake, and the easier one to make.

The `[Defer]` rule rewrites a logger call inside a traced region into a
buffered call, and whether that buffers or calls straight through is decided at
runtime by a hook GraphMend injects at the `torch.compile(...)` assignment
site. That injection is a source transformation, so it only happens in a module
Jac compiled.

Run the entry program under plain CPython and no hook is registered, every
logger call runs inline, and every logger break survives, while the modeling
code genuinely was transformed. A model whose breaks are all logger calls then
reports `3 -> 3, 0% fixed` and nothing about the run looks wrong.

So both arms run `entry.py` under `jac run`, which is also how the paper
describes using the tool: `jac run model.py`, with no changes to model code.

## Which rule each model exercises

| Model | Rule |
|---|---|
| t5, whisper, bart, blenderbot, opus-mt, biogpt, pegasus, longformer | `[Defer]` |
| Phi-4-mini-instruct, Florence-2, Qwen-Audio-Chat | `[Where]` |
| MoLFormer-XL-both10pct, grounding-dino | `[Trap]` |

Phi-4-mini is the paper's Figure 3 worked example. MoLFormer-XL is its
validation-guard model and is opt-in, since unlike the other rows it needs
network access and `trust_remote_code`; its revision is pinned because `main`
no longer imports under transformers 4.52.4.

To confirm which rule fired, look for the markers GraphMend leaves in the
generated bytecode: `__gm_cond_<n>` for `[Where]`, `__jac_log_emit__` and
`__jac_flush_se_buffer__` for `[Defer]`, and `__jac_tensor_eq_assert__` for
`[Trap]`.

## Notes

- **Small configs.** `registry.py` builds most models from a small config, a
  few layers with random weights, so the harness is fast and download-free.
  Graph breaks are structural, so the fix rate and the correctness result carry
  over.
- **Correctness.** Both arms get `torch.manual_seed(0)` so they see identical
  weights. The output tensor is SHA-256 fingerprinted and compared, and the
  input shape is reported per arm so a mismatch is flagged rather than trusted.
- **Not every row should reach 0.** clap-htsat-fused, longformer and
  grounding-dino do not in the paper either. What survives is the paper's
  declared out-of-scope category, so the target for those rows is Table 2's
  percentage, not a clean sweep. Use `run_why` to check that what survives is
  the declared category and not a regression.
- **Two rows need a specific setup to be measured at all.** Florence-2 is
  measured in half precision, because in fp32 its guard is dead code and the
  row would pass vacuously at `0 -> 0`. `stella-en-400M-v5` reproduces its
  Table 2 row only on CUDA with xformers, because its breaks live behind the
  unpadding path; elsewhere it falls back to the model card's no-xformers
  recipe and measures a different, smaller break set.
- **Enabling the code path matters.** Phi-4-mini only takes the LongRoPE branch
  when `rope_scaling.type == "longrope"` is set. The same applies to clap
  (`enable_fusion`), longformer (sequence length not a multiple of the
  attention window) and Florence-2 (half precision).
- **Adding a model.** Add a `_build()` returning `(model, inputs)` and a
  registry entry. Some models need model-specific inputs, for example whisper
  takes `input_features`.
- **`"call": "generate"` measures nothing.** `torch.compile` wraps `forward`
  only, and every other attribute is forwarded to the unwrapped module, so
  `compiled.generate(...)` runs the eager model and records zero graphs. No
  registry entry uses it.
