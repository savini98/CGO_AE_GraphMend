\section{Artifact Appendix}

\subsection{Abstract}

The artifact contains the GraphMend implementation, its three AST-level
transformations (Predicated Data-Dependent Control Flow, Graph-Epilogue
Deferred Side Effects, Predicated Trap Lowering), benchmark drivers for the 27
Hugging Face models of Table~\ref{tab:benchmark}, and scripts for graph-break
detection, correctness checking, full-graph capture, latency and throughput
measurement, profiler collection, and compiler-overhead measurement. It
reproduces the results of Section~\ref{sec:eval}.

Break elimination, correctness and full-graph capture are \emph{CPU-only}: no
GPU, no pretrained weights, and no network for 21 of the 27 models. The latency
and throughput results depend on the GPUs used in the paper and are provided as
scripts that measure on the reviewer's own hardware. A container pins the
software stack; \texttt{scripts/run\_quick.sh} gives a pass/fail functional
result in 10--20 minutes.

\subsection{Description}

\subsubsection{How to access}
Repository {{REPO\_URL}} at commit {{COMMIT}}, cloned with
\texttt{-{}-recurse-submodules}; archived at {{DOI}}. The compiler is not
vendored: \texttt{jaseci/} is the upstream toolchain frozen at a commit and
\texttt{patches/graphmend.patch} is everything GraphMend adds, so the patch is a
direct statement of the contribution. \texttt{scripts/setup.sh} verifies the
pin, applies the patch and fetches the typeshed stubs; it is idempotent, and the
archived copy is self-contained.

\subsubsection{Hardware dependencies}
Any x86-64 or arm64 CPU for break elimination, correctness, full-graph capture
and compiler overhead. \textbf{12\,GB of memory is required}:
\texttt{Phi-4-mini-instruct} peaks near 9.7\,GB while GraphMend compiles the
imported modeling code, and less causes an out-of-memory kill. Latency and
throughput need one NVIDIA GPU; GraphMend is functional on any sufficiently
recent device, but reproducing the magnitudes in Table~\ref{tab:benchmark}
requires the paper's RTX 3090, A40 or H100 configurations.

\subsubsection{Software dependencies}
Python 3.13, PyTorch 2.12.1, Transformers 4.52.4, NumPy 2.4.6, torchvision
0.27.1, \texttt{git}, and Docker for the pinned path; NVIDIA drivers, CUDA 12.6
and Triton 3.7 for the GPU experiments. Versions are pinned exactly rather than
floored: a graph-break count is a property of what TorchDynamo splits on, so a
different PyTorch release can report a different number.

\subsubsection{Data sets and models}
No data set; inputs are synthetic tensors at fixed shapes, seeded so both arms
receive identical weights and inputs, with the shape printed per arm and a
mismatch flagged. The models are the 27 rows of Table~\ref{tab:benchmark}.

\subsection{Experiment workflow}

The functional workflow answers whether GraphMend works, on a CPU with no
network, and exits non-zero on failure:

\begin{verbatim}
bash scripts/run_quick.sh     # 10-20 minutes
\end{verbatim}

\noindent It runs the four rule-level suites, then \texttt{t5-small}
(\textsc{[Defer]}), \texttt{Phi-4-mini-instruct} (\textsc{[Where]}, the
Figure~\ref{fig:phi4} example), \texttt{longformer-base-4096} and
\texttt{clap-htsat-fused}. The last two are expected \emph{not} to reach zero;
a run that fixed them would indicate a problem, not a success.
\texttt{scripts/run\_full.sh} then runs every claim the hardware allows,
skipping the GPU experiments where no CUDA device is visible.

One property of the setup is worth stating, because getting it wrong yields a
clean run that silently measures nothing: GraphMend claims imported third-party
code only under an opt-in that is off by default, and the entry program must be
compiled by Jac rather than run under plain CPython. The shipped scripts handle
both; the README documents them for reviewers writing their own.

\subsection{Evaluation and expected results}

Each claim has one script, named for it.

{\small
\begin{itemize}\itemsep0pt
  \item \texttt{run\_break\_analysis.sh} $\rightarrow$
    Table~\ref{tab:benchmark}: \textbf{21 models fully fixed, 3 partially, 3
    unfixed}, with 25 of 27 rows matching the fix rate.
    \texttt{grounding-dino} reads 56\% against 58\%, one break in seventeen.
  \item \texttt{run\_correctness.sh} $\rightarrow$ Section~\ref{sec:eval}:
    \texttt{output\_ok} is \texttt{yes} on all 27 rows, including those that fix
    nothing. FP32 outputs are bit-identical and greedy-decoded token sequences
    agree.
  \item \texttt{run\_fullgraph.sh} $\rightarrow$ Section~\ref{sec:serving}:
    \texttt{fullgraph=True} fails on every original model and succeeds on every
    transformed one. Both-pass or both-fail is a failure.
  \item \texttt{run\_latency.sh} $\rightarrow$
    Sections~\ref{sec:coldstart}--\ref{sec:steadystate}: breaks reach zero,
    CUDA-graph launches per forward collapse to one, and cold start improves.
  \item \texttt{run\_throughput.sh} $\rightarrow$
    Figure~\ref{fig:throughput}: a gain that tracks the number of CUDA-graph
    launches eliminated and shrinks as the batch grows.
  \item \texttt{run\_compiler\_overhead.sh} $\rightarrow$
    Figure~\ref{fig:overhead}: mean overhead near 11.5\% cold and 1.1\% cached.
\end{itemize}
}

\paragraph{Expected variation.} Deterministic results must match exactly:
break counts, CUDA-graph launch counts, output fingerprints and capture
outcomes. Timings vary with the machine, so cold start is validated against a
floor of $1.5\times$ on any CUDA device rather than an expected value, and
steady state and throughput are reported without a threshold, since a fixed
bound would fail an honest run on different hardware.

\paragraph{Absolute break counts.} The CPU sweep runs in FP32, which is what the
correctness claim concerns, and totals 122 breaks against the 147 of
Table~\ref{tab:benchmark}, which were measured in half precision; 17 of 26 rows
match exactly. The largest group that differs is the BART family, whose
overflow guard leads with \texttt{dtype == torch.float16}. That conjunct is a
static bool, so in FP32 Dynamo folds it away and the data-dependent breaks
behind it do not exist. Measured in half precision via
\texttt{gpu/bench.py -{}-count}, those rows match exactly. The fix rate, which
is what the \emph{Fixed(\%)} column reports, is unaffected.

\subsection{Experiment customization}

Rows run by name (\texttt{run\_break\_analysis.sh t5-small biogpt}), and
\texttt{GM\_GPU\_MODELS} selects a subset for the GPU scripts. Rules are ablated
with \texttt{graphmend\_disable}, taking any of \texttt{trap}, \texttt{where},
\texttt{defer}. To target a model outside the suite, add a \texttt{\_build()}
returning \texttt{(model, inputs)} and a registry entry naming the modules to
transform, then inspect the detected breaks with
\texttt{python -m paper\_eval.run\_why <model> on}, which prints each surviving
break with its cause and source location. Note that a model's breaks often live
in shared \texttt{transformers} modules rather than its own package, so a scope
naming only the model package will miss them.

\subsection{Notes}

Enabling the code path under test matters as much as enabling GraphMend.
\texttt{Phi-4-mini-instruct} takes the LongRoPE branch only when
\texttt{rope\_scaling.type} is \texttt{"longrope"}; \texttt{clap} needs
\texttt{enable\_fusion}; \texttt{longformer} needs a sequence length that is not
a multiple of the attention window; and \texttt{Florence-2}'s guard is dead code
in FP32. \texttt{stella-en-400M-v5} reproduces its 0\% row only on CUDA with
xformers, because its breaks live behind the unpadding path.
